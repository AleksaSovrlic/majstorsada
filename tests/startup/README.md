# Startup and notification regressions

Run `npm run test:startup` for the notification lifecycle, dashboard mount hook and service worker tests. Node 24's VM module flag and TypeScript stripping are used only by the tests. They execute the actual source with isolated Firebase/browser adapters; no runtime dependency was added.

The startup command first compiles the functions, then also checks the real API entrypoint in a fresh network-blocked Node process. The pinned metadata fixture protects all 18 endpoint/trigger definitions and 18 parameter specs; review it deliberately when deployment settings or the Functions SDK change. The backend probe checks deferred phone loading, unchanged three-document role transactions/conflicts, and the actual phone parser before database work. It uses isolated database adapters; the security and OTP emulator suites cover integration separately.

Run `npm run build`, then `npm run test:startup:browser` for the compiled-app browser checks. Requires the same Python/Playwright environment as tests/e2e (see `tests/e2e/README.md`). Set `E2E_PYTHON` to select Python and `E2E_BROWSER_CHANNEL` to select the installed browser; the startup probe defaults to Edge. Port 3344 must be free. The runner owns and stops its server tree.

The browser suite intercepts Auth and account API calls with synthetic fixtures. Only GET requests to the exact local host `http://127.0.0.1:3344` reach a server; all external traffic is blocked, and unexpected endpoints fail the run. The known optional Cloudflare analytics script may be blocked without failing. It persists a synthetic login through Firebase's real browser persistence, then opens fresh contexts for both client and tradesperson headers. Three repetitions of five scenarios make 30 measured navigations: immediate responses, service-worker setup delayed 2 seconds, role response delayed 1 second, both delays, and the Firebase Messaging JavaScript chunk delayed 2 seconds.

The compiled Messaging chunk is discovered by the installed SDK's two error keys (`failed-service-worker-registration` and `token-subscribe-failed`). Exactly one matching `.output/public/_nuxt/*.js` file is required; inspect SDK/build changes if this assertion fails. Every request for that chunk must still be held when the correct header and completed hydration are observed. A monolithic eager import would fail this check. Nuxt may emit a passive SSR `prefetch` before Auth restoration, followed by the actual module import after role confirmation. This optimization removes Messaging from initial module parsing/execution; it does not guarantee that its download begins only after authentication. [Playwright routing disables HTTP cache](https://playwright.dev/python/docs/api/class-browsercontext#browser-context-route), so the isolated test can expose both fetches rather than reuse a speculative response. The test records only their resource type and `Sec-Purpose`/`Purpose` classification and holds every matching request; it does not interpret HTTP fetch count as SDK initialization count. The pure lifecycle suite separately proves single shared initialization. Both roles still require account verification before application mount, each navigation performs exactly one Auth lookup and one role request, and client navigation retains its selected service while worker setup is pending. No email, SMS, push, or production database operation is performed.

`STARTUP_STAGE=before` measures an already compiled old build and omits optimization-only assertions and the new chunk scenario (24 navigations). The default `after` mode runs all 30. Measurements, build identifiers, completed JavaScript resource timings, screenshots and per-scenario medians are saved under ignored `.firebase/startup/`, including `before.json` and `after.json`. The runner verifies that the browser runtime build matches the compiled output. Do not present these synthetic timings as live-user percentiles or actual production API latency; they isolate frontend ordering with mocked network responses.

The lifecycle suite covers exclusion of Messaging from static imports, pending module loading, import failure and retry, single-flight initialization/token sync, browser user activation for the permission prompt, unsupported browsers, initialization/token/write failures and explicit retry, logout and account replacement during async work, permission revocation, selective token deduplication, foreground/background message behavior and job-feed startup while notification work is pending. It does not prove delivery through Google's live FCM infrastructure or OS notification settings; release verification must include an actual recipient device.
